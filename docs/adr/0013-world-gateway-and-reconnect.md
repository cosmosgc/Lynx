# ADR 0013: World gateway sessions, authority, and reconnect

- **Status:** Accepted
- **Date:** 2026-10-24

## Context

`engine_sim` owns an authoritative zone and `engine_net` owns envelopes,
negotiation, replication categories, and interest management, but nothing
composed them. Gameplay clients need a single component that turns
authenticated intent into simulation calls and per-session replication without
each transport re-implementing session rules. Authoring those rules inside a
socket handler would make them untestable without a network and easy to bypass,
because a second transport (WebSocket, UDP, a replay tool, or an in-process
test harness) would need to duplicate them.

Three failure modes were motivating:

1. **Client-chosen identity.** If the action body carries an actor, principal,
   or staff flag, a client can act as another entity or grant itself staff
   visibility. If it carries a session ID or resume token, a client can hijack
   another session's replication stream or replay a captured token.
2. **Whole-zone broadcasts.** A gateway that sends one batch to every session
   leaks hidden objects and private property, and makes bandwidth grow with
   total entities instead of visible entities.
3. **Reconnect gaps.** A dropped connection must not delete the character or
   duplicate actions. It also must not let a stale or replayed token reopen a
   session, and it must not resume from a client-chosen tick.

## Decision

- **New crate `world_gateway`.** It depends on `engine_core`, `engine_sim`,
  `engine_net`, and `game_api`; nothing depends on it yet. It owns no socket,
  runtime, database handle, or clock: callers supply a `Zone`, the server
  handshake, a `ResumeTokenSource`, and an explicit `Millis` timestamp. A
  transport adapter is free to be WebSocket, UDP, or in-process without changing
  gameplay rules.
- **Session identity is server-side.** `SessionClaims` (account, character
  principal, staff flag) are built only by code that has already authenticated
  the player. The client cannot name its session ID, principal, actor, staff
  role, view radius, or resume token. Session IDs are server-issued,
  process-local routing labels, independent of the resume token (so exposing a
  session ID never exposes a credential), and are never accepted from the wire.
- **Action bodies carry intent only.** The accepted `action.request` body has
  exactly `verb`, optional `target`, optional `params`, and optional
  `client_tick`. `deny_unknown_fields` rejects any attempt to include `actor`,
  `principal`, `session`, or similar fields with `ErrorCode::InvalidRequest`
  before the simulation is touched. The actor and principal come from the
  session record.
- **Request IDs are scoped per session.** `Zone` caches action results globally
  by request ID for idempotent retries. The gateway prefixes the client ID with
  the session ID (length-prefixed, so the concatenation is unambiguous) before
  calling `apply_action`, then rewrites `ActionResult::request_id` back to the
  client envelope ID. One session can therefore never replay another session's
  cached result, while retries within a session still return the original
  result exactly once.
- **Concurrent-session policy is server-configurable.** The policy is either
  one connected session per character or one per account. The current gateway
  enforces the per-character policy; per-account enforcement requires trusted
  account claims and is planned. A duplicate under the selected policy returns
  `ErrorCode::Conflict` and never replaces an existing session. A fresh login
  discards an abandoned resume window instead of consuming two slots. Retained
  sessions count against `max_sessions`, so reconnects cannot bypass admission
  limits. With per-character policy, multiple client instances may connect to
  the same server under one account using different characters; per-account
  policy permits only one of those sessions.
- **Resume tokens are short-lived, single-use, and rotated.** A disconnect
  keeps the character in the zone and opens a server-configured resume window
  (default 30 s). The token is opaque, generated by an injected
  `ResumeTokenSource` (`SystemResumeTokens` in production,
  `SequentialResumeTokens` in tests), redacted from `Debug`, and replaced on
  every successful resume. The old token stops working immediately; an unknown
  or expired token returns `ErrorCode::SessionExpired` and the session is
  deleted. Expired windows are swept on connect, resume, and every tick.
- **The client's acknowledgement cursor is clamped.** `session.ack` and resume
  accept the client's last acknowledged tick but clamp it to the authoritative
  tick. Clients cannot pin the server to a future tick or replay an old one to
  suppress replication.
- **Replication is per session and never whole-zone.** Each tick compares
  authoritative `EntityRecord` state with the previous tick to find dirty
  entities, then builds one batch per connected session containing only that
  session's interest delta and audience-filtered updates. A reconnect always
  receives a full owner snapshot (inventories and owner-scoped state) plus a
  fresh interest snapshot; later ticks send deltas.
- **Public snapshots are safe by construction.** `EntitySnapshot` exposes
  identity, prototype, transform, health, interaction surface, door state, and
  owner. Inventories, minds, tags, and extension components are not part of it.
  Owner-only payloads (`OwnerState`) are filtered to the owning principal.
- **Visibility uses tags until a first-class component exists.**
  `visibility.hidden`, `visibility.owner_only`, and `visibility.staff_only`
  map to the interest visibility classes. Player-controlled entities without an
  explicit owner fall back to their character principal as owner.
- **Errors do not close the session.** Malformed bodies, unknown kinds, and
  gameplay rejections produce correlated replies: bad input and unknown kinds
  return `protocol.error`, action outcomes return `action.result`. A session is
  only detached by an explicit disconnect, expiry, a missing actor, or a
  transport-level failure.
- **`ErrorCode::SessionExpired` is new.** Session expiry is distinct from
  authentication failure and from permission denial, so transports and clients
  can tell "log in again" from "you may not do that".

## Consequences

- Gateway rules are deterministic and testable in-process; the unit and
  integration tests cover spoof rejection, interest isolation, resume/expiry,
  token replay, missing characters, duplicate and cross-session request IDs,
  unknown kinds, owner inventory isolation, ack clamping, and handshake
  mismatch.
- A transport adapter still has to authenticate, frame, rate-limit, and attach
  a disconnect. Those concerns stay outside the gateway and can be swapped.
- Because tokens rotate, a client that loses the resume response must log in
  again. This is intentional: replays of a captured token must fail.
- Dirty tracking is a full comparison over zone entities per tick. If that scan
  becomes expensive, `engine_sim` can expose a change journal without changing
  the gateway's delivery contract or wire format.
- Owner-only state is currently an inventory snapshot. Pty, quest, and
  permission-scoped audiences will need explicit audience entries in
  `engine_net` rather than ad-hoc gateway branches.
- The gateway binary, database-backed session store, and rate limiting remain
  future work; `lynx-world` is still a library composition, not a process.
