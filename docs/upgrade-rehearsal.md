# Rust, Bevy, and dependency upgrade rehearsal

Use this process for Rust toolchain, Bevy, and broad dependency upgrades. Keep
each upgrade in its own change so regressions and rollback points stay clear.
The current Rust and Bevy pins are in `rust-toolchain.toml` and
`Cargo.toml`; ADR 0001 defines the compatibility policy.

## Prepare the change

1. Record the old Rust, Bevy, and lockfile versions in the change description.
   Review upstream release notes and identify source, platform, and generated
   project compatibility changes.
2. Change the Rust pin separately from a Bevy upgrade when practical. Update
   `Cargo.lock` intentionally; do not mix gameplay or unrelated refactors into
   the upgrade.
3. For a Bevy minor upgrade, add a `CHANGELOG.md` migration note and treat it as
   an engine minor release at minimum. Explain whether generated projects need
   source or manifest edits and how to apply them.
4. Keep Bevy out of `engine_core`, `engine_sim`, `engine_content`, and
   `game_api`. These crates are the headless, Bevy-free engine surface.

## Run the gates

Run the repository CI gate for the change, including formatting, Clippy,
workspace tests and build, dependency audit, and generated-project validation.
The generated-project job scaffolds a project and runs `doctor`, `validate`,
`build`, `run`, and `test`; repeat it locally when changing the scaffolder or
the compatibility contract.

Check the domain boundary independently:

```sh
cargo check -p engine_core -p engine_sim -p engine_content -p game_api
cargo tree -p engine_core -p engine_sim -p engine_content -p game_api
```

Inspect both dependency trees and confirm neither contains Bevy. For a Bevy
change, also build and launch the graphical client on a supported
desktop target. Confirm the window opens, the offline scene renders, camera and
movement input respond, and closing the window exits cleanly. Record the
platform, GPU/backend, result, and any remaining limitation with the change.

## Generated projects and rollback

Include the migration note and new minimum toolchain/engine requirements in
the release notes when generated projects are affected. Validate a freshly
generated project with the CI workflow above and check the documented upgrade
steps against one project generated by the previous release. Preserve the
previous known-good `rust-toolchain.toml`, `Cargo.toml`, `Cargo.lock`, and
release artifact as the rollback point.

If the upgrade fails after merge, revert the dedicated upgrade commit and
restore its matching lockfile and toolchain pin together. For generated
projects, follow the migration note's compatibility direction; do not assume
that restoring the engine binary reverses source or data migrations. If a
migration is not backward-compatible, document the forward recovery before
starting the upgrade and retain a backup of the project state.

## Automated dependency updates

Dependabot opens weekly Cargo and monthly GitHub Actions update pull requests.
Review each update as a dependency change and require the repository's pull
request CI checks to pass before merging. Batch updates only when the related
packages must move together and the combined diff remains reviewable.
